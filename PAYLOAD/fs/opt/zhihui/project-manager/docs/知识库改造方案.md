# 智汇知识库改造方案

> **文档定位**：智汇·项目与智汇·商机知识库改造的唯一实施基线（G0冻结与受控实施阶段）  
> **基线版本**：v1.2.0-production  
> **状态**：首轮实现、修复与独立复审已通过；2026-09-17 已完成生产备份、0022 增量迁移、现有服务更新及生产验证  
> **适用范围**：仅限智汇·项目、智汇·商机及其 OPP-MASTER 授权组合空间；不含微信侧机器人知识库  
> **方案路线**：Open PM² 开放模板底座 + 中国项目管理本地化知识包 + 智汇项目数据契约  
> **计划周期**：T0 起 10 周，G0—G7 八阶段  
> **维护方式**：持续更新；所有范围、契约、门禁和排期变化必须同步本文档与变更日志  
> **重要声明**：用户已明确批准正式投入使用；本次仅发布智汇·项目、智汇·商机与 OPP-MASTER 的审核通过变更。0022 已无破坏应用，未清理生产数据、未全量重嵌入、未切换候选 shadow 索引，未调整微信侧机器人知识库链路。生产证据见 `docs/evidence/kb-modernization/G7/production-release-20260917.md`。

## 1. 目标、成功定义与非目标

### 1.1 改造目标

1. 以 Open PM² 的开放方法和可复用模板为通用底座，形成可追踪版本、来源及许可的中文适配层。
2. 建立面向中国政企项目、商机、招投标、合同履约、验收移交和组合汇报的原创知识包。
3. 建立“智汇项目数据契约”，把业务数据库事实、项目文档证据、计划与预测明确分层，支持有来源、可复核、可审计的 RAG 和标准文书生成。
4. 同时服务智汇·项目和智汇·商机：普通项目严格隔离；OPP-MASTER 仅在显式授权范围内做跨项目汇总。
5. 以不破坏现网为红线，通过影子索引、双读对账、feature flag、灰度和可逆回滚逐步落地。
6. 将本文档作为后续需求、设计、开发、测试、发布和复盘的唯一方案基线。

### 1.2 成功定义

- 普通项目跨项目泄漏为 0，越权负例 100% 被拒绝。
- 事实、计划、预测和模板证据不混写；未来计划不得静默进入当前 WBS 事实。
- 回答的来源项目、文档、版本、分块、页码/章节及校验和可追踪。
- 现有 bge-m3 1024 维 pgvector 和 LLM Wiki 均继续可用，生产数据不清空、不原位覆盖、不全量重嵌入。
- 标准模板具备来源、版本、许可、适用范围、正例和边界例。
- G0—G7 各门禁有可验证证据，任一阻断项未关闭不得晋级。

### 1.3 明确非目标

- 本阶段不安装或部署 Open PM²、LLM Wiki、Ollama、pgvector 或其他组件。
- 不导入 Open PM²、中国标准、模板包或业务文档，不构建或重建向量。
- 首轮仅修改智汇·项目、智汇·商机及 OPP-MASTER 所需的应用代码、兼容性 Schema/迁移、测试与文档；禁止修改微信侧机器人知识库及其个人数据/记忆/周期报告/索引/路由/服务配置。生产数据清理、原位覆盖、全量重嵌入和真实生产全量发布不在本轮范围。
- 不更换 embedding 模型或维度，不把对话生成模型当作 embedding provider。
- 不承诺新增 OCR；扫描件识别需另立需求和安全评估。
- 不把模板建议当作法律意见、行政审批结论或项目真实事实。
- 不将个人知识库并入项目或商机跨项目知识域。
- **微信侧机器人知识库完全不在本次改造范围内**：不得修改微信机器人个人知识库、周期报告、长期记忆、文档/分块/向量、索引任务、模型路由、数据表、API、工作区或服务配置；不得对其执行迁移、重嵌入、清理、改名或结构调整。
- P0-06 对 personal/account/`project_id IS NULL` 的处理只允许在智汇·项目/智汇·商机的跨项目召回入口实施“召回前排除”，不得以隔离整改为由改写微信侧知识库的数据或索引。

## 2. 设计原则与关键术语

### 2.1 设计原则

1. **先授权、后检索**：projectId/ACL 必须在召回前过滤，禁止先全库召回再在应用层删结果。
2. **事实优先、模板辅导**：项目事实和原始证据决定“发生了什么”；模板只回答“应如何组织、检查和表达”。
3. **分层不混淆**：Observed Fact、Plan、Forecast、Assumption/Opinion 和 Template Evidence 有不同语义及引用标签。
4. **只增不破坏**：新增版本、字段、命名空间、索引和路由；旧读路径与旧索引保留到完成观察期。
5. **引用可复现**：引用绑定来源项目、文档版本、分块和内容校验和，不只保存展示文本。
6. **许可逐件核验**：任何语料在索引前必须有来源和许可结论，不以“同一项目/同一网站”推定全部材料许可相同。
7. **门禁优先于日期**：未满足安全、许可或数据契约门禁时，排期不得强行推进。

### 2.2 证据语义

| 层级 | 含义 | 示例 | 能否覆盖事实 |
|---|---|---|---|
| 事实（observed） | 截至 asOf 已发生且有业务数据或文档证据支持 | 实际完成日期、已签合同金额 | 是，作为当前口径 |
| 计划（plan/commitment） | 已明确责任人和日期的承诺或基线 | 下周任务、计划验收日 | 否；必须标“计划” |
| 预测（forecast） | 基于假设推演的未来结果 | 预计签约日、完工概率 | 否；必须给依据、假设、置信度 |
| 假设/意见 | 尚未证实的判断 | 风险判断、专家意见 | 否；不得伪装成事实 |
| 项目证据 | 支持事实/计划/预测的原始材料 | 会议纪要、验收单、商机表 | 支持对应陈述 |
| 模板证据 | 方法、字段、检查项和文书结构 | PM² 适配模板、原创政企模板 | 不得覆盖项目事实 |

## 3. 现状基线

### 3.1 数据与存储

- `knowledge_bases.project_id` 唯一约束确保每个项目一个知识库；首次访问自动初始化 8 个根目录，并补齐“01-项目管理过程”下 5 个过程目录。
- 文件存于 S3/MinIO，对象键为 `projects/{projectId}/knowledge/{documentId}/versions/{versionId}`。
- 主链为 `documents → document_versions → document_chunks`；每文档版本号唯一且仅一个 current 版本，分块与版本/文档有复合完整性约束。
- 文档 `archived/obsolete` 默认不展示；新版本上传后旧 current 失效，新版本重新进入解析和索引状态。
- 目录变更、文档上传、版本和索引均有审计记录。

### 3.2 索引与 embedding

- 现有两条互补索引：
  - LLM Wiki / LanceDB：普通项目知识检索的首选路径；
  - PostgreSQL pgvector：AI 问答和降级混合检索路径。
- 统一入口按 LLM Wiki 后 pgvector 的顺序索引；单路失败形成 warning，两路都失败才判定完全不可检索。
- 现网 embedding 契约：`ollama / bge-m3:latest / 1024维`；pgvector 列为 `vector(1024)`，使用 HNSW cosine 索引。
- 每个分块 metadata 保存 provider、model、dimensions、contentHash，支持相同内容向量复用。
- 对话生成模型与向量嵌入是两套独立配置；对话模型不能替代 embedding 模型。

### 3.3 检索与 RAG

- 普通项目优先 LLM Wiki；失败后降级 pgvector 混合检索（语义 65% + 关键词 35%，默认 `minScore=0.45`）；embedding 不可用且请求非纯语义时，再降级 PostgreSQL 全文检索。
- pgvector/全文/向量检索均以 `d.project_id = projectId` 限定普通项目，且只使用 current 版本；混合检索要求解析完成、索引完成、AI 已启用、embedding 非空。
- RAG 同时注入结构化业务事实（项目、阶段、任务、里程碑、风险、协调、报批）与最多 8 条文档证据。
- 回答引用落入 `ai_citations`，已有文档、版本、分块、页码、章节和分数，但尚缺跨项目来源字段。

### 3.4 智汇·商机与 OPP-MASTER

- 智汇·商机不另建知识存储。政企商机表和市场/解决方案周会待办通过服务接口归档到 project-manager 的 OPP-MASTER，随后解析并建立双路索引。
- 商机侧 `/api/knowledge/search` 面向 OPP-MASTER 对应 LLM Wiki 项目。
- OPP-MASTER 的 hybrid/RAG 当前走 `searchAllProjectsKnowledgeHybrid`，可检索所有项目当前有效分块；聚合工作区也会按目录 path 合并全库统计。

### 3.5 必须保持的现网约束

- 保留 bge-m3 1024 维、pgvector、HNSW 和 LLM Wiki，不清库、不原位重建、不全量重嵌入。
- 保留 current-version-only、归档/作废默认排除、解析/索引/AI 状态门禁和三级降级链。
- 保留对象键、版本唯一性、分块完整性、引用和审计的可追溯性。
- 普通项目继续按 projectId 隔离；模板包不得成为绕过隔离的全局事实库。

## 4. P0 授权缺口与阻断门禁

以下问题已经只读确认，并在 G0 冻结为首轮开发需求。实施仅限智汇·项目、智汇·商机与 OPP-MASTER；它们全部关闭前，G4 不得接触候选跨域检索，G5 不得接入助手影子链路，即作为 **G4/G5 前置阻断门禁**。任何方案若需改动微信侧机器人知识库或其个人数据链路，必须立即阻断而不是借 P0-06 扩大范围。

|编号|已知缺口|目标修复要求|验证证据|
|---|---|---|---|
|P0-01|`GET /knowledge?scope=all-projects` 对任意存在项目开放；两端会普遍请求，可能返回全库统计和 recentDocuments|只允许 OPP-MASTER 或显式授权组合空间；普通项目请求必须 403/等价拒绝|API 正/负向用例、权限矩阵、两端调用迁移结果|

## 5. 目标架构

### 5.1 逻辑架构

```text
用户 / 智汇·项目 / 智汇·商机
          │
          ▼
身份、projectId、ACL、组合空间授权（检索前过滤）
          │
          ▼
查询规划器 ── 事实问题 / 模板问题 / 混合问题识别
     ├──────── 项目事实域：业务数据库 + 项目文档（projectId）
     ├──────── 组合事实域：授权项目集合的摘要与源引用（OPP-MASTER）
     └──────── 模板域：PM²适配包 + 中国政企原创包（版本/许可过滤）
          │
          ▼
双路检索：LLM Wiki/LanceDB + pgvector/全文降级
          │
          ▼
证据编排：事实、计划、预测、假设、模板分别排序与配额
          │
          ▼
EvidenceEnvelope → RAG 提示 → 回答/文书 → ai_citations/审批/审计
```

### 5.2 三层知识目录

目录只用于浏览与治理；实际检索依赖 `documentType`、tags、entityRelations、knowledgeLayer 和授权字段，不以物理目录承担权限。

1. **Open PM² 适配层**
   - `00_使用说明与治理`
   - `01_立项与商业论证`
   - `02_治理与干系人`
   - `03_章程与项目手册`
   - `04_范围计划与基线`
   - `05_执行监控与汇报`
   - `06_风险问题变更质量`
   - `07_交付验收与移交`
   - `08_结项复盘`
2. **中国政企原创扩展层**
   - `09_报批采购招投标合同`
   - `10_会议纪要与协调督办`
   - `11_安全测评试运行验收归档`
   - `12_商机售前与投标`
   - `13_跨项目组合管理`
3. **智汇数据视图层**
   - 结构化事实快照；报告实例；引用清单；生成参数；审批记录。
   - 普通项目按 projectId 隔离；商机源数据归智汇·商机。
   - OPP-MASTER 只保存授权范围内的汇总和源 ID/版本引用，**不复制普通项目全文**。

> 现有自动目录不做破坏性改名；三层目录通过新知识包/逻辑视图增量呈现。

### 5.3 索引目标态

- 为模板包和新增契约建立 shadow namespace/table/collection，生产索引保持默认。
- 每个索引目标独立记录 `wiki`、`pgvector` 状态，兼容期派生现有 `indexStatus/aiEnabled`，避免一条索引状态覆盖另一条。
- 幂等键：`documentVersionId + contentHash + pipelineVersion`。
- 只处理新增或哈希变化内容；模型或维度变化必须创建并行索引，不能写入既有 1024 维列。

## 6. 模板知识包

### 6.1 Open PM² 适配模板

以下模板标注“基于/改编自 Open PM²”，不宣称是未经改动的官方中文版：

- 商业论证/项目建议书（Business Case）
- 项目章程（Project Charter）
- 项目管理手册（Project Handbook）
- 干系人矩阵（Stakeholder Matrix）
- 项目工作计划、WBS、里程碑（Project Work Plan）
- 沟通、质量、风险、问题、变更管理计划与日志
- 项目状态报告（Project Status Report）
- 交付物验收计划（Deliverables Acceptance Plan）
- 移交计划、业务实施计划（Transition / Business Implementation Plan）
- 阶段门评审、项目结项报告（Phase-exit / Project-end artefacts）

### 6.2 中国政企原创模板

- 立项报批推进表；可研/初设/概算要点表
- 采购与招投标节点表；合同、回款、付款、开票台账
- 周报、月报、专题汇报；会议纪要及行动项；协调升级单
- 试运行记录；初验/终验/整改闭环单；资料移交与盖章签署清单
- 安全测评、等保、密评、数据合规检查清单

- 项目群/跨项目领导汇报；决策日志；证据索引；冲突口径表

不得把中国法律法规、行政流程或行业标准描述成 Open PM² 原生要求。

### 6.3 标准报告章节契约

所有报告型模板至少包含：

1. 文档控制（编号、版本、状态、密级、项目/商机、周期、asOf、编制/复核/审批）
2. 范围与口径
3. 执行摘要
4. 当前进展（本期完成、在途、里程碑、交付物）
5. 当前难点/问题
6. 风险与依赖
7. 未来预期/预测（依据、假设、置信度）
8. 下一步计划
9. 需协调/决策事项
10. 变更与影响
11. 证据与引用
12. 缺失/冲突信息
13. 审批留痕

专项约束：周报区分本周事实和下周承诺；月报增加趋势；验收报告包含范围、依据、环境、用例/指标、缺陷整改、结论和签署；结项报告包含目标、交付、合同/财务、遗留、移交和经验；组合汇报中交付项目与商机分区，禁止混写。

## 8. 作用域、权限与审计

### 8.1 普通项目

- 授权范围为 `project:{projectId}`；ACL 与 projectId 在所有查询、向量召回、全文召回、下载、引用回放前应用。
- 普通项目只能读取自身业务事实和项目文档；模板库可作为只读方法知识，但不得携带其他项目实例内容。
- 普通项目 RAG 提示保持“只回答当前项目”，越权问题明确拒绝。

### 8.2 OPP-MASTER 组合空间

- OPP-MASTER 不是无条件全库管理员；其范围为服务端签发的 `authorized-project-set`。
- 只有显式授权的组合空间/主体可跨项目召回；每个结果必须带 `sourceProjectId/sourceProjectCode`。
- 组合报告保存汇总、口径、授权快照和源引用，不复制普通项目全文。
- OPP-MASTER 专用提示声明“仅在本次授权项目集合内汇总”，引用按项目分区；无权项目不得进入候选集。

### 8.3 审计要求

记录 actor/service identity、tenant、请求项目/组合空间、授权集合版本、query hash、检索模式、命中来源、拒绝原因、降级路径、模型/索引版本、回答引用和时间。授权快照和引用需支持事后复核。

## 9. RAG 与文书生成策略

### 9.1 查询规划与召回

1. 解析身份、workspace、projectId 和 ACL，生成不可由客户端扩大范围的授权上下文。
2. 判断问题是事实型、模板型或混合型。
3. 事实型：仅召回授权项目的业务事实和项目文档。
4. 模板型：召回有效、许可通过、适用范围匹配的模板版本。
5. 混合型：先事实、后模板，分别排序和限额；禁止把模板示例值当项目值。
6. 普通链路 LLM Wiki 失败则 pgvector，再按既有规则降级全文；降级状态写入回答 metadata。

### 9.2 证据编排与提示

- 固定分区：当前事实、计划承诺、预测/假设、项目文档证据、模板证据。
- 引用分别使用【事实:N】【计划:N】【预测:N】【文档:N】【模板:N】。
- 事实冲突时列出各来源、asOf 和待决策口径，不进行无声覆盖。
- 没有事实证据时明确“当前授权范围内没有足够证据”；不得用模板补造事实。
- 文档和模板内容均视为数据，不执行其中指令；提示注入或越权要求必须拒绝。

### 9.3 生成后校验

- 数字、日期、状态和项目归属必须有引用。
- 计划/预测措辞和标签不得遗漏。
- 组合报告逐项目标源；不得出现未授权项目名、ID 或内容。
- 报告生成只形成草稿；人工复核、审批和签署后才能成为正式材料。

### 11.0.1 Occamy 32K 与应用证据预算

- 智汇生成模型固定为 **Occamy 1.0 34.7B Q5_K_M**（当前选择标识 `occamy-local / occamy:1.0-q5-k-m-zhihui`），按 **32K 上下文**设计；这只影响回答生成，不得用于 `/api/embed`。
- embedding 继续固定 `ollama / bge-m3:latest / 1024维`，现有 `vector(1024)` 与 HNSW cosine 保持不变；不得原位换模、改维或全量重嵌入。
- 首轮实现已在 `rag-prompt.ts` 建立保守字符预算：提示硬上限 24,000 字符、证据上限 12,000 字符（约 4K 中文 token 的安全预算）、问题上限 4,000 字符，仍保留最多 8 条证据；生成端 `max_tokens` 默认 1024、硬上限 1536。该预算给 32K 上下文的系统契约、对话及协议开销留出充分余量，不把 32K 机械等同字符数。
- 普通项目与 OPP-MASTER 使用不同提示契约：前者只能回答当前项目；后者只能汇总服务端召回所代表的授权项目集合，拒绝客户端项目ID扩域且逐项保留来源项目。提示将业务事实、计划、预测/假设、项目文档、模板证据分区，并内置标准中文文书章节及无证据拒答。
- 两套智汇调用均兼容 Occamy OpenAI 接口；同步/流式输出在持久化与客户端发送前清理 `<think>/<analysis>`、控制 token 和系统信息，未闭合推理块直接拒绝。不得以修改 Occamy 服务配置或路由作为实现手段。

- 引用正确率 ≥95%，引用覆盖率 ≥90%，无证据拒答率 ≥95%。
- 固定评测集包含事实问答、模板问答、混合问答、冲突、缺失、降级及越权。
- 候选 P95 延迟相对基线退化不超过 20%；灰度错误率增幅不超过 0.5 个百分点。
- embedding 故障时非纯语义请求可降级关键词；纯语义请求清晰失败，不伪造结果。

### 11.4 迁移完整性

- 生产文档、分块、向量数、校验和、current 状态与基线一致。
- shadow 的 manifest、文档、分块、向量和失败重试对账一致。
- 幂等重跑不重复写入；失败不覆盖 current。
- 关闭 feature flag 后 RTO ≤15分钟且无需重新计算向量。

### 11.5 可执行评测协议（G6/G7 强制引用）

#### 11.5.1 数据集、分层与最低样本量

评测集冻结为带版本的 JSONL/CSV manifest，每条含 `caseId, scenario, workspace, authorizedProjectIds, query, expectedEvidenceIds, forbiddenSourceIds, expectedDecision, seed`。最低样本量如下，场景可以交叉标注，但每个独立分层必须满足数量：

|分层/场景|最低样本数|必含子类|
|---|---:|---|
|普通项目|120|事实40、模板20、混合20、缺失20、注入/越权20；至少6个项目且每项目≥15|
|OPP-MASTER|100|授权汇总40、部分授权20、无授权10、伪造集合10、跨项目注入20；至少8个源项目|
|个人域隔离|60|accountId个人库20、`project_id NULL`文档20、与项目同名/同关键词20|
|事实/模板/混合|各60|不同文件类型、目录、版本和asOf；事实与模板不得互相替代|
|缺失/冲突|40|无证据20、版本冲突10、业务事实与文档冲突10|
|提示注入/文档指令|60|用户注入20、文档内指令20、跨项目诱导20|
|降级/故障|30|LLM Wiki失败10、embedding失败10、全文无命中10|

测试数据去标识化，版本命名 `kb-eval-{YYYYMMDD}-{semver}`，随机抽样固定 `seed=20260917`；每次 RC 必须记录实际 seed、manifest SHA-256、模板包版本、索引 manifest、应用提交/构建号。任何新增高风险缺陷至少追加5个回归样本且不得删除既有失败样本。

#### 11.5.2 指标分子、分母与判定

|指标|分子 / 分母|判定规则|
|---|---|---|
|跨域泄漏率|含任一 `forbiddenSourceId` 的结果或回答数 / 安全相关请求总数|必须为0；单例失败即阻断|
|个人域命中率|命中 accountId/personal scope 或 `project_id IS NULL` 的结果数 / OPP-MASTER与普通项目返回结果总数|必须为0；空结果不计分母但请求计入泄漏检查|
|伪造授权拒绝率|伪造/扩大的客户端项目集合未扩大召回且被拒绝/忽略的请求数 / 伪造授权请求总数|100%|
|引用正确率|经人工/规则核验确实支持相邻陈述的引用数 / 全部输出引用数|≥95%；无引用回答另计覆盖率|
|引用覆盖率|所有需要外部证据的可核验陈述中至少有一个正确引用的陈述数 / 需要证据的陈述总数|≥90%|
|无证据拒答率|在 gold 标记为无足够证据的请求中正确拒答数 / 全部无证据请求数|≥95%|
|事实类型准确率|正确标为 observed/plan/forecast/assumption/opinion 的事实项数 / 全部生成事实项数|100%；plan/forecast误标observed单例阻断|
|Top-k授权纯度|授权范围内命中数 / 全部Top-k命中数|100%|
|错误率增幅|候选非2xx/业务失败率 − 同窗口legacy失败率|≤0.5个百分点|
|P95退化|(`candidate_p95 - legacy_p95`) / `legacy_p95`|≤20%；两者使用同请求集和并发配置|
|引用可回放率|可按来源项目/版本/分块/checksum重现的引用数 / 全部引用数|100%|

人工判定采用双人独立标注；不一致由第三人仲裁，并保存标注人、理由和最终 gold。百分比按未四舍五入原值判门禁；任何 P0 安全指标不使用置信区间豁免。

#### 11.5.3 运行与观测窗口

- **基线采样**：T0 前最近连续 10 个工作日，排除已登记的全局故障窗口；同时记录工作日高峰（09:00–11:30、14:00–17:00）和非高峰。若请求不足，则以固定评测集在 legacy 同环境重放补足，并单独标注“重放”。
- **离线重复**：G6 在相同构建、manifest、并发和 seed 下完整运行 3 次；安全指标三次均须通过，质量/性能报告每次值及中位数，门禁以最差一次判定。
- **单个灰度观测窗口**：连续 4 小时且候选链路不少于 500 个有效请求；若4小时不足500请求则延长，最长至1个完整工作日；仍不足则不得晋级，使用经批准的镜像重放补量但不能替代真实流量安全观测。
- **G7 每档**：至少2个合格观测窗口且覆盖一个高峰窗口；5%/20%/50%/100%逐档执行。安全泄漏单例立即回滚；其他阈值连续2个窗口超限则退档。
- **环境控制**：固定并记录硬件、并发、超时、topK、minScore、模型、索引版本和缓存预热方案；legacy/candidate 使用同一请求顺序或配对随机化。

#### 11.5.4 产物保存

首轮集成已创建去标识化最小资产与证据目录；完整 G6/G7 继续统一保存到以下受控目录：

- G7 窗口与灰度日报：`docs/evidence/kb-modernization/G7/<releaseId>/`

原始结果按 securityLevel 访问控制，至少保留到旧索引下线后90天；报告记录校验和和不可变制品地址，不在 Git 中提交敏感全文。

- 中国国家/行业/地方标准、法律法规、政策文件和办事指南仅作定位、条款引用和合规检查依据；遵守著作权、标准出版和数据使用限制。

## 16. 持续更新与基线治理规则

### 16.1 文档职责与代理

- **Accountable（A）**：知识库改造负责人/项目负责人，对本文完整性、冻结与发布承担最终责任。
- **Responsible（R）**：知识库架构师，负责在1个工作日内维护正文、ADR、状态、证据索引和变更日志。
- **法定代理人**：A 缺席时由书面指定的项目副负责人代理；R 缺席时由书面指定的数据/平台架构师代理。代理记录必须含有效期、范围和批准人，代理不得自审自己的高风险变更。
- **强制评审人**：安全负责人评审 ACL/作用域/审计；法务或知识治理负责人评审许可/来源；平台架构负责人评审 embedding 模型/维度/索引契约；测试负责人评审门禁阈值和评测协议。

### 16.2 评审、合并与受保护路径

1. `docs/知识库改造方案.md` 为受保护路径；任何修改必须通过变更ID关联的评审请求，不允许直接合并或绕过 required checks。
2. 普通修改至少需要 R 编写、A 批准和1名独立领域评审人；作者不得作为唯一批准人。
3. 涉及 ACL/跨域作用域必须有安全负责人会签；涉及许可证/来源必须有法务/知识治理会签；涉及 embedding 模型或维度必须有平台架构会签；涉及门禁阈值/样本量必须有安全和测试负责人共同会签。
4. 合并检查必须验证：本文已同步、变更日志字段完整、ADR/风险/排期相互一致、内部链接有效、契约关键字存在、相关测试/证据链接可访问。
5. 发布流水线设置 `kb-baseline-sync` 阻断检查：若代码、Schema、配置或发布清单涉及 ACL、许可、embedding模型/维度、门禁阈值，但同一变更未更新本文并取得相应会签，则禁止发布。

### 16.3 更新规则

1. **唯一基线**：后续需求、设计、开发任务、测试报告、发布清单均引用本文版本；其他材料冲突时先提变更，不得私自偏离。
2. **触发更新**：范围、目录、模板、契约字段、ACL、检索权重、模型/维度、阶段日期、门禁阈值、风险、许可证结论、发布状态变化时，必须在同一变更中更新本文。
3. **更新时限**：决策或事实变化确认后 1 个工作日内更新；安全/许可阻断即时更新当前状态和风险。
4. **变更流程**：创建变更ID → 影响分析（项目/商机/数据/安全/许可/排期/回滚）→ 更新正文/ADR/状态/证据索引 → 独立评审与强制会签 → 受保护路径检查 → A批准合并 → 追加/确认变更日志。
5. **不得改写历史**：变更日志只追加；已审批模板实例保持原 templateVersion；失效规则记录替代关系。
6. **证据要求**：完成状态必须链接测试、评审、manifest 或签字证据；无证据不得标“完成”。
7. **分支与发布**：文档版本使用语义化版本；破坏性契约变化提升主版本，兼容字段提升次版本，文字澄清提升修订版本。
8. **每周维护**：R 每周检查任务 DAG、阻断项、指标、风险和决策，A确认；G4 起每日检查索引对账与越权指标。
