## 3. 旧执行器为什么不能复用

现有工具绑定旧的“双方均未迁移且台账为空”基线，必须拒绝直接用于当前生产：

- `ict-g3-backup-verify.sh` 固定要求 `14/1015/21/0/20/0`，无法为当前64条商机、5张商机ICT表和非空台账生成合法恢复点。
- `ict-g3-release.sh` 固定要求旧 pre-state，执行时还会重放商机0005，并在任意迁移后失败时调用 empty-only 回滚。
- `ict-g3-post-verify.sh` 固定要求 opportunities=0、ICT台账=0，并会执行回滚事务探针；不适用于当前非空台账。
- `0021_0005_empty_only.sql` 会因商机台账非空主动拒绝，且绝不能绕过该拒绝。
- 11:54旧恢复点和现有旧G3审计不得作为当前生产的恢复依据。

## 4. 必须新增的差异化工具

在A1/A2/A3执行前，先完成并审查以下工具；工具开发与隔离静态验证不代表生产授权：

1. `scripts/ict-g3-differential-backup-verify.sh`
   - 接受且只接受精确的当前差异化基线；业务计数、journal、项目/商机结构和商机台账计数全部匹配才允许备份。
   - PG客户端主版本必须等于服务器主版本。
   - custom-format备份必须恢复到严格随机库并验证完整基线。
   - 记录备份SHA、大小、restore list和非敏感计数；权限700/600。

2. `scripts/ict-g3-differential-release.sh`
   - production前置条件：新恢复点小于24小时、最终候选清单逐项匹配、独立A3授权、`IMPORT_CHANGE_TRACKING_ENABLED`在确定的配置源显式启用。
   - 开关校验不得只grep单一文件：systemd EnvironmentFile先注入、dotenv只补缺失且不覆盖。工具必须同时验证配置源无冲突，并在服务启动后从受控进程环境或等价行为探针确认运行时实际为enabled；证据只记录规范化结论，不记录环境内容。
   - 冻结后再次核验精确pre-state。
   - **只执行项目0021**，不得执行商机0005。
   - 迁移后要求journal=21、项目表3、项目约束18；商机表5、列4、约束23和商机台账计数保持不变。
   - 启动API后再启动Web，检查四端点和认证边界；四个systemd单元必须`active/running/Result=success/NRestarts=0`，任一不满足即NO-GO。
   - 生成权限600的脱敏审计文件。

3. `scripts/ict-g3-differential-post-verify.sh`
   - 验证14/1015/21/64/0、journal21、ICT表8、商机列4、项目/商机约束18/23。
   - 商机批次/实体/字段/current/审计至少应与pre-state完全一致；若观察窗口允许业务写，则必须改为捕获冻结时水位并证明只发生已授权追加，不能用硬编码零值。
   - 禁止对商机表执行任何探针写入。
   - 项目探针只能在A2随机库执行；production验证只读。

4. `database/rollback/0021_public_empty_only.sql`
   - 只允许检查并撤销`public.import_batches`、`public.import_batch_entities`、`public.import_field_changes`和0021对应journal。
   - SQL中不得出现任何`opportunity`表的DROP、ALTER、DELETE或TRUNCATE；也不得触碰遗留`public.import_jobs`（当前268行，它不属于ICT-1三表）。回滚后必须反向证明商机5表、4列、23约束及冻结水位台账全部保持不变。
   - journal删除谓词固定为0021的`created_at=1789202600000`，执行后必须断言journal精确回到20；不得按“最后一条”或模糊范围删除。
   - 仅当项目三表总行数为0时允许执行；一旦出现首个项目批次，无论状态为何，该回滚永久拒绝。
   - 必须先在A2随机库完成apply→verify→public-only rollback→商机台账不变的完整演练。

5. 新恢复方案
   - 旧`0021_0005_empty_only.sql`在生产永久禁止且不得放宽守卫。
   - 项目0021是expand-only；生产失败优先关闭项目ICT写入口并前向修复。只有项目三表全空、A2已证明新public-only回滚安全、且A3授权明确包含该失败分支时，才允许执行`0021_public_empty_only.sql`。
   - 若public-only守卫拒绝或执行失败，服务保持冻结并转人工处置，不得触碰商机结构或台账。
   - 如发生不可接受且无法前向修复的故障，整库恢复只能在独立明确授权下使用新A1恢复点；恢复会覆盖恢复点之后的业务写，执行前必须再次冻结并计算数据差异。

### 阶段P1：A1恢复点

1. 取得A1明确授权。
2. 冻结证据水位，但不停止服务、不迁移。
3. 用PG16同主版本工具生成备份。

6. 清理随机库并保存权限受控证据。

失败处理：立即停止；不得进入A2/A3；不得删除失败备份证据。

### 阶段P2：A2隔离演练

1. 取得A2明确授权。
2. 从P1恢复点建立随机演练库。
3. 只执行项目0021；不得重放商机0005。
4. 验证journal20→21、项目表0→3、项目约束0→18。
5. 验证商机64条和全部非空台账计数、关联、约束均不变。
6. 在尚未创建项目批次时运行`0021_public_empty_only.sql`，验证journal21→20、项目表3→0，商机结构和台账完全不变；随后重新apply 0021并复验。
7. 在随机库验证项目preview/confirm及开关关闭行为；创建首个项目批次后必须证明public-only回滚以固定错误拒绝且数据保留。
8. 删除随机演练库。

失败处理：修复工具或代码后重新生成候选；不得进入A3。

### 阶段P3：A3生产项目0021

1. 取得包含会话ID和固定确认短语的A3明确授权。
2. 确认P1恢复点小于24小时，候选哈希未变化。
3. 将`IMPORT_CHANGE_TRACKING_ENABLED=true`显式写入权威环境文件；此配置写入属于A3范围，实际值只记录规范化结论。
4. 冻结四服务，要求MainPID=0且四端口无监听。
5. 再次核验精确差异化pre-state；任一计数漂移即取消本次执行并恢复服务。
6. 只运行项目0021，验证journal21、项目3表/18约束。
7. 验证商机结构和非空台账未变化。
8. 按API→Web顺序恢复服务并完成只读自动验证。
9. 输出`READY_FOR_EDGE_G3_SMOKE`，不得输出GO。

失败处理：
- 项目迁移前失败：直接恢复服务。
- 项目迁移成功后应用层失败：优先保持项目表、显式关闭项目ICT写入口并前向修复；若项目三表仍全空、A2演练PASS且A3授权明确包含该失败分支，可执行public-only空回滚。守卫拒绝或失败时保持服务冻结并人工处置。
- 一旦项目侧存在任意批次，禁止public-only结构回滚。
- 只有整库不可恢复故障且用户再次明确授权时才允许从P1恢复点整库恢复。

### 阶段P4：A4 Edge E1～E8

A4授权前必须先修订现有迁移后Edge模板：旧模板中的“商机可信scope 200空列表”已因正式环境存在64条商机而失效，不得继续作为验收断言。新模板应验证可信scope返回200、总量与冻结水位一致、64条记录可只读访问且`latestImportChange`契约存在，同时不得记录实际tenant、内部业务UUID或敏感认证信息。修订后的E1～E8只做读取与兼容性验证，不创建导入批次，不修改64条商机或项目数据。

### 阶段P5：24小时观察与A5 GO

观察API错误率、四服务`ActiveState/SubState/Result/NRestarts`、数据库约束错误、导入失败、历史查询和数据计数；以A3启动窗口的`NRestarts=0`为起点，24小时内任一非计划重启即延长观察并保持NO-GO。观察期通过后由用户明确决定GO。
