# 开发改造日志与导入变化追踪契约基线

> **唯一变更基线（Single Source of Change Truth）**
>
> 本文件是“智汇·项目”和“智汇·商机”后续开发改造、排期、任务计划、契约决策、验收证据与回滚记录的**唯一变更基线**。任何需求、设计、字段、接口、迁移、排期、负责人、依赖、状态、风险或发布结论发生变化，必须先更新或在同一提交中更新本文件；仅存在于聊天、工单、代码注释或口头沟通中的变化不视为已批准。所有后续任务完成前必须更新下方对应状态并附可复核证据。

- 基线版本：`ICT-1.0`
- 当前状态：**代码、自动化验证与独立审查已通过；发布硬门禁尚未满足（代码可集成，禁止发布）**
- 适用应用：智汇·项目（`project-manager`）、智汇·商机（`bussiness-manager`）
- 数据边界：不直接修改生产数据；不操作 MinIO 正式文件
- 决策原则：预览先于写入、批次不可变、字段变化可解释、稳定业务键不依赖行号、当前态与历史态分离、失败不切换当前批次

## 1. 本次目标与范围

### 1.1 目标

1. 对每次导入生成不可变批次，导入前预览与上一成功批次的字段级差异。
2. 两个应用用同一变化语义、方向、严重度和 API 包装结构。
3. 导入成功后可在列表标记有变化的实体，并可按实体、批次查看旧值/新值及来源行。
4. 首次导入、无变化、修改、清空、新增、归档均有确定且可测试的语义。
5. 变化台账只追加、不覆盖，并与执行批次、操作者、校验摘要关联。

### 1.2 本轮业务范围

| 应用 | 纳入的导入对象 | 当前实现基础 | 本轮变化追踪重点 |
|---|---|---|---|
| 智汇·项目 | 实施计划/WBS 当前快照（任务及由其派生的阶段） | `import_jobs`、`tasks.snapshot_id/is_current/archived_at` 已支持快照切换；事务内按 `projectId + wbsCode` 更新/新增/归档 | 任务关键字段差异、缺行归档、阶段派生变化、项目当前快照指针 |
| 智汇·商机 | 政企商机表 | 已有 Excel 解析预览；数据库 `opportunity.opportunities` 有 `tenant_id + code` 唯一约束，但当前预览用行号生成 `IMP-*`，列表仍是静态 JSON | 冻结可靠商机键、预计签单时间等关键字段变化、落库与批次台账 |

不在本轮范围：生产库历史数据直接修订、MinIO 正式对象处理、OCR/向量化/AI 问答、市场/交付周会待办变化追踪、跨租户合并、自动删除历史实体。

## 2. 现状审阅与约束

### 2.1 智汇·项目

可复核代码证据：

- `apps/api/src/db/schema.ts`：项目编码唯一；任务当前态唯一键为 `project_id + wbs_code WHERE is_current=true`；任务与阶段已有 `snapshot_id/is_current/archived_at`。
- `apps/api/src/modules/imports/import-service.ts`：支持预览校验；任务快照在项目行锁和事务内按 WBS 编号新增/更新，将缺失任务归档，并写 `task_snapshot/activated` 审计。
- `docs/AI案卷评查项目实施计划表-导入字段映射.md`：已记录中文表头、系统字段、状态/进度/日期转换。

缺口：预览未返回相对上一成功批次的字段差异；执行过程直接覆盖任务当前值，未保存逐字段 old/new 台账；列表和详情没有统一变化摘要。

### 2.2 智汇·商机

可复核代码证据：

- `../bussiness-manager/database/0001_opportunity_foundation.sql`：商机稳定约束为 `UNIQUE(tenant_id, code)`，包含 `expected_sign_date` 等主数据字段。
- `../bussiness-manager/apps/api/src/server.ts`：政企商机预览从第 5 行读取，映射 15 类字段；当前 `code=IMP-${rowNumber}`，该值随排序变化，不能作为跨批次稳定键；`GET /api/opportunities` 尚未启用数据库列表。
- `../bussiness-manager/apps/web/public/opportunities.json`：现有展示数据有 `MASTER-*` id、`sourceSheet/sourceRow` 及扩展 `masterFields`，但 JSON id 与数据库 `code` 尚未形成权威映射。

缺口：政企商机导入只有基于服务器路径的预览，没有确认执行、不可变批次、字段台账或数据库列表；行号键会造成误判新增/归档。

**冻结约束**：商机实现不得继续以 Excel 行号生成跨批次业务键。无法得到可靠 `code` 的行只能在预览中标记 `stable_key_missing` 并禁止确认；不得用模糊名称静默覆盖现有商机。

## 3. 统一术语与导入批次语义

### 3.1 批次状态机

`previewed -> validating -> applying -> succeeded | failed | cancelled`

- `previewed`：已解析、标准化并计算差异，尚未写业务当前态。
- `validating`：确认前重新校验预览指纹、上一批次和稳定键。
- `applying`：事务内写当前态和变化台账。
- `succeeded`：事务提交后才可成为 scope 的 current batch。
- `failed/cancelled`：不得改变 current batch，保留错误供审计；重试必须创建新批次。

批次最小字段：

| 字段 | 约束 |
|---|---|
| `id` | UUID，不可复用 |
| `app` | `project` / `opportunity` |
| `scopeType/scopeId` | 项目端为 `project/{projectId}`；商机端为 `tenant/{tenantId}` |
| `kind` | 项目端 `implementation_plan`；商机端 `government_enterprise_opportunity` |
| `sourceName/sourceChecksum` | 原文件名与 SHA-256 |
| `mappingVersion/normalizationVersion` | 本基线初始均为 `ICT-1` |
| `baseBatchId` | 同 scope/kind 上一成功批次；首次为 `null` |
| `previewFingerprint` | 规范化行、baseBatchId、映射版本的确定性 SHA-256 |
| `status` | 使用上述状态机 |
| `counts` | total/created/modified/unchanged/cleared/archived/invalid |
| `actorId/actorName/requestId` | 操作者与链路审计信息 |
| `createdAt/appliedAt` | 带时区时间 |

同一源文件可重复上传并形成不同批次，但若 `sourceChecksum + baseBatchId + mappingVersion + scope` 相同，确认接口必须幂等返回已成功批次，禁止重复写台账。

### 3.2 对比基准

1. 只与**同一应用、scope、kind 的上一成功批次**对比，绝不跨项目或跨租户。
2. 预览生成后若 current batch 已变化，确认返回 `409 import_base_batch_changed`，要求重新预览。
3. 比较使用标准化后的类型值；原始单元格值仅用于溯源，不参与相等判断。
4. 差异与业务当前态、current batch 指针在同一数据库事务提交。
5. 批次、批次实体快照、字段变化记录均为 append-only；撤销通过补偿批次，不物理删除历史。

## 4. 稳定业务键

| 应用/实体 | 权威稳定键 | 规则 | 禁止项 |
|---|---|---|---|
| 项目 | `projects.id`；外部匹配可用唯一 `projects.code` | 导入 API 已绑定 `projectId`，文件名只做提示 | 禁止仅按项目名称写入 |
| 项目任务 | `projectId + normalize(wbsCode)` | WBS 必填；NFKC、trim；保留层级点号；同批重复直接报错 | 禁止追加行号修复重复键；禁止以任务名匹配 |
| 项目阶段 | `projectId + normalize(phaseName)`（导入匹配键），持久化仍用 phase id/code | 同名标准化后唯一，由任务行派生 | 禁止以自动生成 `IMP-*` code 做跨批次匹配 |
| 商机 | `tenantId + normalize(code)` | 文件必须提供权威商机编号；既有 `MASTER-*` 可作为 code；NFKC、trim、英文字母大写 | 禁止 `IMP-${rowNumber}`、sourceRow、名称模糊匹配作为写入键 |
| 商机组织 | 当前不独立追踪；由商机 `customer` 映射/展示 | 本轮保留文本快照，后续另立组织去重契约 | 禁止因客户名称轻微变化迁移商机键 |

兼容策略：若历史商机文件没有编号，预览可用 `normalize(name) + normalize(customer)` 生成 `matchCandidate` 供人工选择现存 code；只有显式绑定并记录 `bindingEvidence` 后方可确认。候选绝不是稳定键，名称变更也不得自动新建或覆盖。

## 5. 字段字典与标准化

### 5.1 通用标准化 `ICT-1`

| 类型 | 标准化规则 | 清空表示 |
|---|---|---|
| 文本 | Unicode NFKC；去首尾空白；CRLF→LF；普通单行内部连续空白折叠为一个；多行正文保留换行并去行尾空白 | 空单元格、仅空白、`null`→`null`；字符串“无/暂无”默认是文字，除非字段另有枚举规则 |
| 日期 | Excel serial、Date、`YYYY/M/D`、`YYYY-M-D` → `YYYY-MM-DD`；非法日历日期报错，不静默顺延 | `null` |
| 数值 | 去千分位；十进制定点语义；金额单位按字段换算后比较 | `null` |
| 百分比 | `20%`→20；0~1 的比例值仅在项目进度字段按现有映射转为 0~100；越界报错 | `null` |
| 枚举 | 中文别名映射为系统枚举；未知值报错并保留 rawValue | `null`（必填枚举不允许清空） |
| 业务键 | NFKC + trim；商机 code 大写；WBS 不折叠层级标点 | 不允许清空 |
| JSON/长文本 | 对象键稳定排序后比较；正文按文本规则，不做语义相似判断 | `null` |

差异比较须区分 `undefined`（文件未提供该列，不更新、不产生变化）与 `null`（列存在且单元格为空，产生 `cleared`）。

## 6. 变化方向、类型与严重度

### 6.1 变化类型（`changeType`）

| 类型 | 精确定义 | 实体结果 |
|---|---|---|
| `initial` | scope/kind 不存在上一成功批次 | 建立基线；所有非空字段可记 initial，但 UI 默认折叠，不算 modified |
| `unchanged` | 同键实体存在且所有纳入字段标准化值相等 | 不写逐字段台账；批次实体摘要记录 unchanged |
| `created` | 当前批次出现稳定键，基准批次不存在 | 写实体 created 及非空字段 new value |
| `modified` | 同键字段 old/new 均非空且不等 | 写逐字段变化 |
| `cleared` | 文件提供该列，old 非空、new 为 null | 写逐字段 cleared；高/关键字段要求预览确认 |
| `archived` | 完整快照中，基准存在的稳定键在当前批次缺失 | 软归档 `isCurrent=false/archivedAt`；绝不物理删除 |

首次导入绝不把所有记录标记为“新增告警”；其批次 `baseline=true`，页面显示“首次基线”。无变化批次仍可成功并保留批次记录，`hasChanges=false`、changes=0。

本轮两类文件均按**完整快照**处理，因此缺失稳定键表示 archived。未来若支持增量文件，必须新增显式 `mode=delta`，在本文件升版；不得靠文件名猜测。

### 6.2 方向（`direction`）

统一枚举：`increase | decrease | postponed | advanced | from_empty | to_empty | state_forward | state_backward | changed | none`。

- 数值：new > old 为 increase，反之 decrease。
- 日期：new > old 为 postponed，new < old 为 advanced。
- 空值：null→value 为 from_empty；value→null 为 to_empty。
- 阶段按 `lead < qualified < discovery < proposal < negotiation < won`；进入 lost/closed 单独按状态严重度处理。
- 文本/负责人/分类为 changed；initial/unchanged 为 none。

### 6.3 严重度（`severity`）

统一枚举：`info | low | medium | high | critical`。字段基础重要性见字段字典，再应用以下确定性规则：

1. stable key 冲突、跨租户/跨项目、非法枚举、预览指纹不一致：critical，阻止确认。
2. 实体 archived、商机 expectedSignDate 清空、任务 plannedEndDate 清空、商机进入 lost/closed：critical，必须显式确认。
3. expectedSignDate 推后：≤7 天 medium，8~30 天 high，>30 天 critical；提前为 low（清空例外）。
4. 任务 plannedEndDate 推后：≤7 天 medium，>7 天 high；已完成任务日期被修改为 high。
5. 任务状态 backward、进度下降、负责人清空：high；正常状态前进/进度上升：low。
6. 金额下降：high；毛利率下降：high；金额或毛利率清空：critical；上升：low。
7. 普通文本变化继承字段基础重要性但最高 high；from_empty 默认降低一级（critical 字段最低 medium）。

批次 `maxSeverity` 取其所有实体变化最大值，计数必须按 severity 返回。

## 7. 冻结数据契约

### 7.1 批次实体快照

建议两个库按各自 schema 建同语义表（命名可遵循项目规范）：

```text
import_batches(
  id, app, scope_type, scope_id, kind, mode='snapshot', source_name,
  source_checksum, mapping_version, normalization_version, base_batch_id,
  preview_fingerprint, status, counts_json, actor_id, actor_name, request_id,
  created_at, applied_at
)
import_batch_entities(
  id, batch_id, entity_type, business_key, target_entity_id, source_sheet,
  source_row, raw_json, normalized_json, row_hash, change_type,
  max_severity, changed_field_count, created_at
)
import_field_changes(
  id, batch_id, batch_entity_id, entity_type, business_key, target_entity_id,
  field_key, change_type, direction, severity, old_value_json,
  new_value_json, old_display, new_display, derived, created_at
)
```

硬约束：

- `UNIQUE(batch_id, entity_type, business_key)`；字段台账 `UNIQUE(batch_id, entity_type, business_key, field_key)`。
- `old_value_json/new_value_json` 保存规范化类型值；敏感字段若未来纳入必须脱敏，本轮不记录联系人电话。
- 索引至少覆盖 `(scope_id, kind, created_at desc)`、`(target_entity_id, created_at desc)`、`(batch_id, severity)`。
- 表应用最小权限；普通列表接口不返回 raw_json。
- 数据保留期在运维策略明确前不得清理；清理只能归档批次原文件引用，不得先删审计台账。

```json
      "changes": [
        {"fieldKey": "plannedEndDate", "changeType": "modified", "direction": "postponed", "severity": "high", "oldValue": "2026-09-01", "newValue": "2026-09-20", "oldDisplay": "2026-09-01", "newDisplay": "2026-09-20"}
      ],
      "errors": []
    }
  ],
  "errors": []
}
```

预览要求：返回 created/modified/cleared/archived 和关键 unchanged；支持分页时 summary 必须针对完整批次；任何阻断错误令 `confirmable=false`。不得在预览阶段更新业务实体。

### 7.3 确认、查询和审计 API

- `POST .../imports/:batchId/confirm`，请求含 `previewFingerprint`、`baseBatchId`、`confirmCriticalChanges:boolean`。
- critical 变化存在但未确认：`409 import_critical_changes_confirmation_required`。
- 成功返回 `batch + summary`；相同幂等请求返回同一结果。
- `GET .../imports/:batchId/changes?entityKey=&severity=&changeType=&page=` 查询批次变化。
- `GET .../entities/:entityId/changes?limit=` 查询实体历史。
- 列表实体统一增加：

```json
{
  "latestImportChange": {
    "batchId": "uuid",
    "changedAt": "ISO-8601",
    "changeType": "modified",
    "changedFieldCount": 2,
    "maxSeverity": "high",
    "fields": ["plannedEndDate", "status"]
  }
}
```

只有最新成功批次中 created/modified/cleared 的当前实体展示标记；archived 默认不在当前列表展示，可在“已归档”筛选中查看。无变化和首次基线不显示风险角标。

审计最小事件：`import.previewed`、`import.confirmed`、`import.failed`、`import.cancelled`、`import.rollback_applied`。内容含 scope/batch/baseBatch、源 checksum、mapping/normalization 版本、counts、actor/requestId；不得记录文件正文或鉴权凭据。

### 7.4 原子性与并发

- 确认时锁定 scope（项目行或租户级 advisory lock），重新检查 baseBatchId 和 fingerprint。
- 一个事务完成：业务实体 upsert/软归档、批次实体、字段台账、current batch 指针、审计事件。
- 任一行失败则整批失败；不得出现部分成功的 current snapshot。
- 知识库/对象归档等外部副作用在事务后异步执行，其失败记录 warning，不反向破坏已成功数据库批次；本轮不操作正式 MinIO。

## 8. 页面交互验收契约

1. 上传后先进入预览页，显示基准批次、文件 checksum 摘要、created/modified/cleared/archived/unchanged/invalid 计数。

## 11. 风险与控制

| 风险 | 影响 | 控制/门禁 |
|---|---|---|
| 商机沿用行号键 | 大量误新增/归档、历史串线 | stable_key_missing 阻止确认；先完成人工绑定或补编号 |
| 标准化版本改变 | 同值被误判变化 | 批次固化 normalizationVersion；升级需回归和本文件升版 |

| 跨项目/租户查询 | 越权 | 所有查询从鉴权 scope 过滤，禁止只按 batchId/entityId 查询 |
| 大文件差异耗时 | 超时/内存 | 文件/行数限制、流式解析或分块、数据库批量写；summary 全量一致 |
| 业务写成功但外部归档失败 | 状态不一致 | 外部副作用后置且 warning 可重试；数据库批次不回退为半成功 |
| 迁移锁表 | 服务不可用 | 先增表/索引、分步迁移、预演锁耗时；发布窗口执行 |

## 12. 回滚策略

### 12.1 代码/发布回滚

1. 发布前记录镜像/提交版本和迁移版本于 T8 证据。
2. 功能开关 `IMPORT_CHANGE_TRACKING_ENABLED` 默认可关闭；关闭后保留旧读取能力，但禁止绕过新稳定键执行危险商机写入。
3. 代码回滚到上一版本时，新台账表保持只读，不删除；避免旧代码无法识别的新当前态时，应同时关闭导入入口。

### 12.2 数据迁移回滚

- 采用 expand/contract：先增加 nullable 字段/新表/索引，再回填，再启用约束；确认稳定后才考虑删除旧结构。
- 迁移必须提供 down 或经过验证的人工逆操作；但已经产生的批次台账不得物理删除。
- 商机历史 stable key 回填必须先输出冲突报告；一对多/多对一冲突不得自动处理。

### 12.3 业务批次回滚

回滚不是删除批次，而是创建 `rollback` 补偿批次，以目标成功批次的 normalized snapshot 作为新输入，完整走预览、critical 确认、事务应用和台账；记录 `rollbackOfBatchId`。这样当前态恢复而审计链不断裂。失败批次无需业务回滚，因为它从未切换 current batch。

触发条件：批次造成错误归档/关键字段错误、越权写入、差异算法版本缺陷。越权或数据泄露同时按安全事件处理并暂停导入入口。
